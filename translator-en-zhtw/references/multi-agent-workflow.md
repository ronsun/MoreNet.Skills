# 多代理翻譯流程（操作手冊）

本檔是 SKILL.md「多代理模式」的完整執行細節。讀本檔的是 **orchestrator**（接到翻譯請求、握有完整 skill 的那個你）。`references/design-rationale.md` 是這套架構的學理依據；本檔只談**怎麼做**。

## 進入本流程的前提

多代理模式在**使用者於 SKILL.md 的模式詢問中選了多代理**時啟用（skill 每次翻譯都會問要走標準還是多代理）。

它存在的理由只有一個：**LLM 翻長文時，單一 context 會品質衰退、跨段風格與術語會漂移。** 多代理把每段隔離翻譯（context 乾淨）再由整合者統一全篇，藉此維持品質與一致性。內容愈長愈划算；若使用者對很短的內容也選多代理，照辦即可，但開銷會不成比例。

## 為什麼要拆成多代理

單一 agent 用 LLM 逐段翻長文，context 會愈疊愈長、品質衰退；每段各開新對話又會風格/術語不一致。解法是拆成三種角色：

- **Orchestrator（你）**：不親自翻譯。負責分段、派工、收集、協調整合、寫檔。
- **翻譯子代理**：各自只翻**一個段落**，context 乾淨、品質高。只讀**濃縮規則**（省 token）。
- **整合者**：拿到全部段落的初稿，用**完整規則**逐段重譯並統一全篇術語/風格/語氣。

token 效率的關鍵：完整規則只在整合階段載入一次；N 個翻譯子代理各自只讀小小的濃縮規則檔，且彼此 context 隔離，不互相污染。

## Claude 子代理怎麼運作（你需要知道的機制）

- 用 **Agent 工具**（`subagent_type: "general-purpose"`）派出子代理。你在 `prompt` 參數裡寫清楚它的任務，它在**全新、隔離的 context** 執行，結束時把最後訊息回傳給你。
- **並行**：在**同一則回應**裡發出多個 Agent 呼叫，它們會同時跑。這就是段落並行翻譯的做法。
- 子代理看不到你的對話歷史，也不會自動載入 skill。**它需要的東西，你要嘛寫進 prompt，要嘛叫它去讀檔**。叫它讀檔比整段貼進 prompt 省 token。
- 子代理回傳的只有它的最後訊息（你看得到，使用者看不到）。所以要它**只回譯文**，不要寒暄。
- 子代理不需要、也不應再往下派子代理。所有派工都由你（orchestrator）做。
- 下方 prompt 範本裡的 `<skill 目錄>` 你要換成**實際絕對路徑**（子代理的工作目錄可能不同，相對路徑會找不到檔）。例如 `C:\Users\<you>\.agents\skills\translator-en-zhtw\references\condensed-rules.md`。

## 完整流程

### 步驟 1：分段

以自然段落為單位切分；單段超過 3000 字元才強制再拆。給每段一個 id（`p1, p2, …`）。記下段落總數 N。

### 步驟 2：並行派出翻譯子代理（一段一個，純 LLM）

在**同一則回應**裡，對每段發一個 Agent 呼叫。一次並行的段數建議**上限 6–8 個**；段落更多就分幾批並行（每批等回來再發下一批），避免一次塞太多。

每個子代理的 `prompt` 用下方範本。注意：**只給該段 + 前後段各一句摘要 + 目前已鎖定的術語**，不要把整篇貼進去（那就失去隔離的意義了）。

```
你是英譯台灣繁體中文的單段翻譯子代理。直接從英文原文翻譯。

第一步：讀 <skill 目錄>/references/condensed-rules.md，照它的規格翻譯。

【文體】<技術文件/學術/商務/口語/行銷…，沿用原文文體>
【本段原文】
<paragraph source>

【上下文線索（僅供理解指代，不要翻譯這部分）】
前段結尾：<prev paragraph 末句，或「（本段為開頭）」>
後段開頭：<next paragraph 首句，或「（本段為結尾）」>

【已鎖定術語（一律照用，不得自創別名）】
<term lock list，例如：authentication → 驗證；JWT → JWT（JSON Web Token）。無則寫「（尚無）」>

輸出規格：
- 只輸出本段中文譯文，不要任何前言、解釋或客套。
- 最後另起一行 `術語/疑點：` 列出你新建的術語對照、以及任何你無法確定的指代或歧義（沒有就寫「無」）。
```

收集每個子代理回傳的：`段落 id、原文、初稿譯文、術語/疑點`。

### 步驟 3：彙整術語記憶

把所有子代理回報的「術語/疑點」併成一份**術語/風格記憶**（結構化、精簡，不留長草稿）：

```
術語鎖定：
  authentication → 驗證
  JWT → JWT（JSON Web Token）
  ...（衝突的擇一並標記，交整合者最後定奪）
人名/稱謂：<統一譯法>
語氣基調：<全篇一致的文體層級>
待決疑點：
  p7 的 "he" 指代不明 → ...
```

這份記憶就是跨段一致性的載體，會傳給整合者。

### 步驟 4：整合者逐段重譯（全文逐段重譯 + 分批護欄）

整合者用**完整規則**逐段重譯每一段。怎麼派，看段落數：

**N ≤ 6（或內容明顯不長）**：派**一個**整合者，一次處理全部。prompt 用下方範本，`【段落清單】`放全部段落。

**N > 6**：分批，每批 5–6 段，**循序**（不是並行，因為要把術語記憶往下傳）。每批的整合者：

- 收完整規則 + 本批段落（原文＋初稿）＋**截至目前的術語/風格記憶**＋**上一批最後一段的定稿末句**（作為銜接）。
- 回傳本批定稿 ＋ **更新後的術語/風格記憶**。
- 你把更新後的記憶帶入下一批。

如此每個整合者 context 有界，不會重蹈長文衰退，但每段仍由握有完整規則的整合者重譯過、且全篇術語/風格連續。

整合者 `prompt` 範本：

```
你是英譯台灣繁體中文的整合者，握有完整規則並負責全篇一致性。

第一步：讀 <skill 目錄>/references/linguistic-rules.md（完整規則），以它為準。

你的工作：對【段落清單】每一段，比對原文與初稿，用完整規則**重譯**成定稿。
重點不是微調初稿，而是：
1. 全篇術語、人名、稱謂、語氣層級統一（依【術語/風格記憶】，發現更好的譯法可更新並回報）。
2. 修掉初稿殘留的英式骨架、hedge 升降格、claim strength 位移。
3. 解決【待決疑點】：依跨段上下文判斷指代，定稿寫出明確指代。
4. 段間銜接自然（承接【上一批銜接句】）。

【文體】<...>
【術語/風格記憶】
<彙整後的記憶>
【上一批銜接句】<上一批最後一段定稿末句，或「（本批為開頭）」>
【段落清單】
[p<id>]
原文：<source>
初稿：<first-pass>
---
（重複每一段）

輸出規格（嚴格遵守，方便我解析）：
[p<id>]
<該段定稿譯文>
===
（每段之間用 === 分隔；全部段落輸出完後）
【更新後術語/風格記憶】
<更新後的記憶>
```

### 步驟 5：寫入輸出

依整合者回傳的 `[p<id>]` 順序拼回，逐段寫入輸出檔案（**逐段落地原則仍適用**：寫入成功才算該段完成）。EPUB 等情境再套各自的 HTML/排版規則。

### 步驟 6：收尾

只輸出最終譯文給使用者（除非要求診斷）。若有未解決的待決疑點（如真正歧義、原文疑似有誤），在最後一次性列給使用者確認。

## 成本與品質提醒（給你判斷用）

- 多代理模式的開銷遠高於標準模式（N 個翻譯子代理 + 1～數個整合者）。它存在的理由是「翻長文、又要維持品質與一致性」，內容不長時標準模式就夠，別用多代理。
- 段落級已是成本/品質的平衡點。若使用者要求單句級，提醒對方成本會隨句數線性暴增。
- 整合者「全文逐段重譯」是使用者指定的最高品質取向；若使用者更在意成本，可改口頭請你把整合者降級為「只統一術語/風格 + 重譯被標記的弱段」。
