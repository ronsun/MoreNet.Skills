# 出版級三審流程（長文／整章／整本的多代理手冊）

讀本檔的是 **orchestrator**——接到翻譯請求、握有完整 skill 的那個你。本流程照搬出版社譯書的分工：

1. **譯者**（子代理，並行）：逐工作單位執行完整三遍法，產出初稿。
2. **中文編輯**（子代理，循序）：**只看中文、不看英文**，以台灣編輯的耳朵統稿——統一聲音、磨接縫、修節奏。母語感的最後把關。
3. **雙語校訂**（子代理，並行）：對照原文查編輯後的稿子，只抓忠實失真——包含編輯改出來的失真。

最後由 orchestrator 做一道**機械式終檢**（步驟 6）：段數、連結、標記、術語一致性——這是程式能查的東西，別靠肉眼。

為什麼要拆：單一 context 翻長文會品質衰退、跨段漂移；而「不看英文的編輯」只有用乾淨 context 的獨立代理才做得到——看過英文的腦袋讀不出母語者的違和感。這正是人類出版流程讓中文編輯不懂原文也能潤稿的原因。

成本遠高於單代理，但本 skill 的取向是品質優先；內容達到「長文」等級（單一 context 難以維持全程品質）就走這條路。

## 機制備忘（Agent 工具）

- 用 Agent 工具（`subagent_type: "general-purpose"`）派子代理；prompt 寫清楚任務，它在全新隔離的 context 執行，只回傳最後訊息。
- **並行**：同一則回應裡發多個 Agent 呼叫。一批建議 4～6 個，批間收齊再發。
- 子代理看不到你的對話，也不會自動載入 skill：需要的東西寫進 prompt，或叫它讀檔（給**絕對路徑**，例如 `C:\Users\<you>\.agents\skills\translator-en-zhtw\references\craft.md`）。
- **子代理輸出走檔案，不走回覆**：叫每個子代理把成品用 Write 寫進工作檔，回覆只回一行 `DONE <id> <段數>`。長譯稿塞回 orchestrator 的 context 會爆，而且下一批就讀不到了。
- 要求子代理只回約定格式，不寒暄。子代理不再往下派工。

## 流程

### 步驟 0：通讀、定調與蒐詞（orchestrator 親自做）

1. 通讀全文（書籍級：讀目錄＋抽讀開頭、中段、結尾章節），掌握文體、口吻、論證或敘事結構。

2. **譯入既有語料時，先蒐詞（關鍵一步，別跳過）。** 續譯某本書的後續章節、接手他人譯稿、或要對齊已出版前文時，新內容的用詞必須和既有中文一致，否則整本讀起來像兩個人翻的。做法：
   - 把既有的中文譯文全抓出來（EPUB 就抓 `translated` 段落；其他格式抓對應的中文）。
   - 對**競爭譯法**做字頻統計，一組一組比。例：型別 vs 類型、建構子 vs 建構函式、串流 vs 資料流、回傳 vs 傳回、開發者 vs 開發人員。
   - 以「**多數派 ＋ 官方譯名**」定案（技術書可查該廠商的台灣官方用語，如微軟術語庫），寫進術語表鎖定。
   - 語言關鍵字、型別名、API 名等**保留英文**的清單也一併定下來。
   - 這一步在動筆前做完。定調段與所有子代理 prompt 都帶著這份已鎖定的術語表。

3. 產出**定調筆記**（之後每個子代理都會收到）：
   ```
   【文體錨點】<craft.md §1 六種之一＋一兩句補充，如：技術文件體，資深工程師對同行說話、該下判斷就下判斷>
   【讀者與姿態】<寫給誰、作者對讀者的態度>
   【定調段】<你親自譯好的開頭一段樣稿——全篇的音叉>
   【術語表】<term → 譯法；人名、稱謂、組織名；保留英文清單。含步驟 0.2 蒐到的既有語料鎖定詞>
   【特殊約定】<情境限制，如 EPUB 的標點規則、客戶指定譯名、註腳 id 規則>
   ```
   定調段必須自己譯到滿意才開工——它決定全篇的天花板。

### 步驟 1：分工作單位

以語意斷點切分：小節、場景、或 3～8 個自然段一單位。給每單位一個 id（`u1, u2, …`）。單位要夠大，讓譯者能在篇章層次重寫；不要退化成逐段甚至逐句。

**單位大小的操作值**：約 5～8 千字元一單位較好調度。硬斷點放在標題邊界；剩下的零星小節（不足半個單位）併進相鄰單位，別讓一個單位只有一兩段。每個單位記下它涵蓋的段落 id 範圍，供步驟 6 對帳。

### 步驟 2：譯者子代理（並行，逐單位三遍法）

每單位一個譯者，prompt 範本：

```
你是英譯台灣繁體中文的譯者，負責一個工作單位，目標是母語等級——譯文單獨拿給台灣讀者看，不會被懷疑是翻譯。

第一步：讀 <絕對路徑>/references/craft.md（寫作工藝）與 <絕對路徑>/references/audit.md（查核規程）。

然後對【本單位原文】執行三遍法：
1. 讀懂：吃透意思、語氣、claim strength，記下術語與疑點。
2. 蓋上原文，用中文寫：依【定調筆記】的錨點與定調段，把意思當自己的話寫出來。資訊順序、句子分合自由；不要 1:1 對齊英文句子。
3. 對照查核：依 audit.md 逐句查忠實；失真處從語意重寫，不打補丁。最後只讀中文做誦讀檢查。

【定調筆記】
<貼上定調筆記全文>

【本單位原文】
<unit source，每段標好段落 id>

【上下文（僅供理解，不要翻譯）】
前一單位結尾：<末段或末句，或「（全文開頭）」>
後一單位開頭：<首句，或「（全文結尾）」>

輸出：用 Write 寫入 <工作檔路徑>，格式如下，回覆只回一行 DONE <id> <段數>。
<本單位中文譯文，逐段標回段落 id>
---術語新增---
<term → 譯法，一行一組；無則寫「無」>
---疑點---
<指代不明、原文歧義、原文疑誤，一行一項，註明段號；無則寫「無」>
```

收齊後：合併術語新增到術語表、彙整疑點、確認每個工作檔都已落地。**術語衝突的裁決**：子代理各自提的譯法若打架（甲寫建構函式、乙寫建構子），由 orchestrator 依「既有語料多數派＋官方譯名」定一個，回頭統一，並記進術語表。後續批次的譯者收到的是更新後的術語表。

### 步驟 3：中文編輯（循序統稿，不看英文）

**絕對不給編輯英文原文**——這是本流程的靈魂。編輯只看中文，才聽得出違和。

長度在單一代理可負荷範圍 → 一個編輯管全篇；太長 → 分批循序，每批帶上前一批的定稿結尾與風格備忘。prompt 範本：

```
你是台灣出版社的中文編輯。手上這份稿子出自多位譯者，你的工作是把它統成「同一位台灣作者寫的」。你看不到原文，也不需要——你只對中文負責。

第一步：讀 <絕對路徑>/references/craft.md。

逐段編輯：
- 聲音與用詞統一（依【定調筆記】與定調段）。
- 單位接縫處讀起來要連貫，該補的承接、該刪的重複開場，動手改。
- 節奏平的段落、悶的句子、不像人話的對話——重寫。
- 只讀中文仍覺得「這句怪怪的、像翻譯」→ 大膽改順。

紅線（碰到就停手，列入回報，不要自己改）：
- **主張強度（claim strength）一個字都不要動。** 你為了讓句子順，很容易把「可能」改成「會」、「建議」改成「必須」、「似乎」改成「就是」、把「當初若…本可以…」的假設寫成既成事實——這是本流程最常見的失真來源，而且你看不到原文、無從察覺。凡是牽涉可能／或許／傾向／建議／應該／一定這類強度的字，維持原樣。
- 術語、數字、專名、程式碼識別字：沒把握就不要動。

【定調筆記】
<貼上>
【術語表】（這些譯名已鎖定，不得更動）
<貼上>
【上一批定稿結尾】<或「（本批為開頭）」>
【稿件】
[u<id>]
<該單位中文初稿>
---
（逐單位）

輸出：用 Write 寫入 <編輯工作檔>，格式為 [u<id>] 分節、段落 id 保留，回覆只回一行 DONE，並附：
---語意存疑處---
<你改動時沒把握、或懷疑原稿有語意問題的地方，附段號；無則寫「無」>
```

### 步驟 4：雙語校訂（並行，只查忠實）

編輯統稿後，每單位派一個校訂者對照原文。prompt 範本：

```
你是雙語校訂者。這份中文稿已經過編輯統稿，母語感由編輯負責；你只做一件事：對照英文原文，抓語意失真。

第一步：讀 <絕對路徑>/references/audit.md，依 §1 語義清單與 §2 claim strength 規則逐句查核。

**優先獵殺 hedge 升格。** 編輯為了通順，最常把弱主張改強——may→會、suggest→證明、consider→就、probably 消失、反事實假設變既成事實。逐句拿譯文的強度和原文對，只要譯文比原文強或比原文弱，就是失真。這是你要抓的第一類，也是命中率最高的一類。

其餘照 audit.md：遺漏、增添、否定方向、數字、指代、術語、交叉引用連結是否掉了。

【本單位英文原文】
<source>
【編輯後中文】
<edited>
【術語表】
<貼上>
【編輯標記的語意存疑處】<與本單位相關者；無則寫「無」>

輸出：用 Write 寫入 <校訂工作檔>，回覆只回一行 DONE <id> <失真項數>。
若全數通過：只寫 PASS。
若有失真，逐項寫：
- 位置：<段號＋引譯文原句>
- 問題：<遺漏/增添/強度位移/否定/數字/指代/術語/連結 等，說明對照>
- 修正句：<從語意重寫的整句替換——維持編輯後的行文聲音，不要退回直譯>
```

orchestrator 套用修正：只替換校訂者給出的句子；修正句若明顯破壞行文（退回翻譯腔），以語意為準自己重寫該句。

**要不要退回重譯，看失真的來源，不看數量。** 舊規則「一個單位修正超過三處就退回重譯」太死。真正的判準是：
- 失真集中在**編輯改出來的回歸**（hedge 升格、為順句而動強度）→ 底稿是好的，直接套用校訂修正即可，不必重譯。本串就有單位被抓出五到七處，全是編輯升格弱主張，套修正就結案。
- 失真來自**底稿本身**（整段理解錯、大量遺漏、術語全錯）→ 這個單位退回步驟 2 重譯，補不如重做。

### 步驟 5：套用修正、逐單位落地

依校訂結果把每個修正句換進編輯後的稿子，逐單位寫入最終輸出檔。**逐單位落地**：寫一個確認一個，不在記憶裡囤全篇。EPUB 等情境在這一步套各自的 HTML／排版規則（雙語段落結構、class、註腳 id 加 `-tw` 等）。

### 步驟 6：機械式終檢（orchestrator 親自，用程式查）

肉眼會漏，這一關全部用腳本掃。長文靠這道關卡兜底：

- **段數對帳**：最終輸出的譯文段數 = 原文應譯段數，逐段 id 一一對上，不多不少不重複。這是最容易出事、也最容易查的一項。
- **交叉引用連結**：原文每個 `<a href="...">第 X 節／圖 X</a>`，譯文都要有對應連結，屬性原樣。**譯文連結數應等於原文連結數**——少了就是漏（這是跨章書籍最常見的漏失）。
- **行內標記與實體**：`<code>`／`<strong>`／`<em>` 數量對得上；HTML 實體 `&lt;` `&gt;` 沒被還原成 `<` `>`。
- **標點約定**：情境有規定就查（如 EPUB 禁非原文的冒號／分號／破折號）。
- **術語一致性掃描**：拿鎖定術語表掃全文，抓漏網的競爭譯法或陸式用詞。
  - **這一步會有假陽性，命中要看上下文再改，別無腦取代。** 子字串比對常誤傷：「這類型別」會被當成「類型」、「參數組成」會被當成「數組」、「有代表性的實例」的「實例」其實是 real-world example 的正確中文。逐個確認是真違規還是誤判。

- 結構完整性：XML／HTML well-formed、無重複 id、編碼與換行符與原檔一致（別把 CRLF 改成 LF、別動 BOM）。

### 步驟 7：交付

1. 抽讀跨單位接縫各一段（只讀中文），確認聲音連續。
2. 交付譯文。
3. 未解決的疑點（真歧義、原文疑誤、疑似原書錯誤）一次性列給使用者，附段號，讓對方定奪——不要自己在譯文裡替原作者改錯。

## 護欄

- **逐單位落地**：每階段產出即寫檔，不在記憶中囤全篇。
- **子代理輸出一律走檔案**，回覆只回 `DONE`；譯稿不塞回 orchestrator 的 context。
- **並行上限 4～6**；批間收齊再發。
- **術語表單向增長**：只有 orchestrator 能改；子代理只能提議。衝突由 orchestrator 依「既有語料多數派＋官方譯名」裁決。
- **編輯永遠看不到英文；校訂者永遠不管風格**——兩個角色的紀律互為保險。使用者若要求省成本，可跳過步驟 3 或 4（明確告知風險：跳過編輯損母語感，跳過校訂損忠實），但不要合併它們給同一個代理。
- **機械式終檢不能省**：段數、連結、標記是程式該查的，別靠三審的肉眼。
